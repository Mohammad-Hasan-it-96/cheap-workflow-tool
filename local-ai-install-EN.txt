REALISTIC EXPECTATION - read this before you start
--------------------------------------------------
With 4 GB of VRAM the GPU cannot hold the model. It will only hold attention
weights and the KV cache. The expert weights live in system RAM and are read
by the CPU. Therefore:

  - Expected generation speed: 8 - 13 tokens/sec
  - Expected prompt processing (prefill): slow, this is the known weak spot
    for MoE models on CPU. A 20k-token prompt can take 60-120 seconds.
  - GPU speedup over pure CPU: roughly 1.2x - 1.5x. Useful, not dramatic.

8-13 tok/s is fine for an overnight batch runner. It is not fine for
interactive chat. Plan accordingly.

2. INSTALL llama.cpp  (CUDA build for Windows)
================================================================================

WHY NOT JUST OLLAMA?
Ollama does not expose --n-cpu-moe. That flag is the entire reason this setup
works on a 4 GB GPU: it keeps the MoE expert tensors on the CPU while leaving
attention, the router, and the KV cache on the GPU. Without it you either do
not fit in VRAM at all, or you fit and get no benefit.

WHICH CUDA VERSION?
Your driver (581.95) supports both CUDA 12.4 and 13.3 builds. Use the
12.4 build. It is the lower-risk choice for a Turing-generation Quadro and
has a smaller runtime download.

You need TWO zips:
  llama-b<NNNNN>-bin-win-cuda-12.4-x64.zip   <- the binaries
  cudart-llama-bin-win-cuda-12.4-x64.zip     <- NVIDIA runtime DLLs

The second one is NOT optional. Without it llama-server.exe fails instantly
with a missing-DLL error and no useful message.


--------------------------------------------------------------------------------
SCRIPT: D:\ai\bin\install-llamacpp.ps1
--------------------------------------------------------------------------------
# install-llamacpp.ps1
# Downloads the newest llama.cpp Windows CUDA 12.4 build + CUDA runtime DLLs.
$ErrorActionPreference = "Stop"

$Dest = "D:\ai\llama.cpp"
$Tmp  = "D:\ai\_tmp"
New-Item -ItemType Directory -Force -Path $Dest, $Tmp | Out-Null

[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12
$hdr = @{ "User-Agent" = "llamacpp-setup" }

Write-Host "Querying GitHub for the latest build that ships a win-cuda-12.4 asset..."
$releases = Invoke-RestMethod "https://api.github.com/repos/ggml-org/llama.cpp/releases?per_page=15" -Headers $hdr

$binAsset = $null
$rtAsset  = $null
foreach ($r in $releases) {
    $b = $r.assets | Where-Object { $_.name -like "llama-*-bin-win-cuda-12.4-x64.zip" } | Select-Object -First 1
    if ($b) {
        $binAsset = $b
        $rtAsset  = $r.assets | Where-Object { $_.name -like "cudart-llama-bin-win-cuda-12.4-x64.zip" } | Select-Object -First 1
        Write-Host "Found release: $($r.tag_name)"
        break
    }
}
if (-not $binAsset) { throw "No win-cuda-12.4 asset found in the last 15 releases." }
if (-not $rtAsset)  { throw "Binaries found but cudart runtime zip is missing in that release." }

foreach ($a in @($binAsset, $rtAsset)) {
    $out = Join-Path $Tmp $a.name
    Write-Host "Downloading $($a.name) ..."
    # curl.exe is far faster than Invoke-WebRequest for large files
    curl.exe -L --fail --progress-bar -o $out $a.browser_download_url
    if ($LASTEXITCODE -ne 0) { throw "Download failed: $($a.name)" }
    Write-Host "Extracting $($a.name) ..."
    Expand-Archive -Path $out -DestinationPath $Dest -Force
}

Write-Host ""
Write-Host "Done. Verifying:"
& "$Dest\llama-server.exe" --version
--------------------------------------------------------------------------------

Run it:

    powershell -ExecutionPolicy Bypass -File D:\ai\bin\install-llamacpp.ps1

SUCCESS LOOKS LIKE: a version line printed, no DLL error.

================================================================================
3. CRITICAL NVIDIA SETTING - DO NOT SKIP
================================================================================

By default, when a CUDA allocation exceeds VRAM, the Windows driver silently
spills into system RAM instead of returning an out-of-memory error. Your
server will still "work" but at maybe 1 tok/s, and you will have no idea why.

Turn this off so you get a clean error instead:

  1. Open NVIDIA Control Panel
  2. Manage 3D settings  ->  Global Settings  (or Program Settings for
     llama-server.exe)
  3. Set "CUDA - Sysmem Fallback Policy"  ->  "Prefer No Sysmem Fallback"
  4. Also set "Power management mode" -> "Prefer maximum performance"
  5. Apply

Now if you over-allocate, llama.cpp fails loudly and you just raise
--n-cpu-moe by 2. That is the whole tuning loop.

--------------------------------------------------------------------------------
SCRIPT: D:\ai\bin\start-server.ps1
--------------------------------------------------------------------------------
# start-server.ps1
# Usage:  .\start-server.ps1                    -> safe defaults
#         .\start-server.ps1 -NCpuMoe 18 -Ctx 65536
param(
    [int]$NCpuMoe = 24,        # gpt-oss-20b has 24 layers; 24 = all experts on CPU
    [int]$Ctx     = 65536,     # MEASURED: fits at 3489/4096 MiB with q8_0 KV
    [string]$Model = "D:\ai\models\gpt-oss-20b-F16.gguf",
    [string]$Alias = "gpt-oss-20b",
    [switch]$NoQuantKV         # q8_0 KV is ON by default; -NoQuantKV uses f16
)

$Bin = "D:\ai\llama.cpp\llama-server.exe"
if (-not (Test-Path $Bin))   { throw "llama-server.exe not found. Run install-llamacpp.ps1 first." }
if (-not (Test-Path $Model)) { throw "Model not found: $Model" }

# Not named $args: that is an automatic PowerShell variable.
$serverArgs = @(
    "-m", $Model,
    "--alias", $Alias,
    "--n-cpu-moe", $NCpuMoe,   # keep MoE experts of N layers on CPU
    "-ngl", "99",              # offload everything else it can to GPU
    "-c", $Ctx,                # context window
    "-np", "1",                # ONE slot. -np defaults to auto, and the KV pool
                               # is shared across slots - with 2 slots this -c
                               # is split in half and the agent silently gets
                               # 32k, not the 64k measured here.
    "-t", "6",                 # 6 PHYSICAL cores. Do not use 12.
    "--jinja",                 # REQUIRED for tool calling to work
    "--host", "127.0.0.1",
    "--port", "8080",
    "--metrics"
)
if (-not $NoQuantKV) { $serverArgs += @("--cache-type-k", "q8_0", "--cache-type-v", "q8_0") }

Write-Host "Launching: $Bin $($serverArgs -join ' ')`n"
& $Bin @serverArgs
--------------------------------------------------------------------------------

First launch:

    powershell -ExecutionPolicy Bypass -File D:\ai\bin\start-server.ps1

Watch the startup log for these lines:
    llama_model_loader: ... 24 layers
    load_tensors: CUDA0 model buffer size = ...    <- confirms GPU is used
    main: server is listening on http://127.0.0.1:8080

In a SECOND PowerShell window, check it actually answers:

    # DO NOT use curl.exe with inline JSON here. PowerShell 5.1 eats the
    # backslash escapes before curl.exe ever sees them, and llama-server
    # answers with a confusing HTTP 500:
    #   parse error at line 1, column 2 ... last read: '{'
    # That is a SHELL bug, not a server bug. Proof: the same server answers
    # fine from a browser at http://127.0.0.1:8080/
    #
    # Use Invoke-RestMethod instead - it builds the JSON itself:

    $body = @{
        model      = "gpt-oss-20b"
        messages   = @(@{ role = "user"; content = "Reverse a string in Python. Code only." })
        max_tokens = 120
    } | ConvertTo-Json -Depth 5

    $r = Invoke-RestMethod -Uri "http://127.0.0.1:8080/v1/chat/completions" `
             -Method Post -ContentType "application/json" -Body $body

    $r.choices[0].message.content
    $r.timings | Format-List          # prompt_per_second / predicted_per_second

    # If you get HTTP 503 {"message":"Loading model"} - that is NORMAL.
    # The model is 13.8 GB. Wait for it and retry. Or poll properly:
    #   do { Start-Sleep 5; try { $h = Invoke-RestMethod http://127.0.0.1:8080/health } catch {} }
    #   while ($h.status -ne "ok")

And check VRAM headroom while it is loaded:

    nvidia-smi --query-gpu=memory.used,memory.total --format=csv

Write down the "memory.used" number. That is what you will optimize next.

7. TUNE --n-cpu-moe   -- ALREADY DONE, MEASURED ON THIS MACHINE 2026-09-07
================================================================================

You do not need to run a sweep. It was run on your hardware and the answer is
settled. Keep this section for reference / for when you switch models.

THE THEORY (still true in general):
    Lower --n-cpu-moe  = more experts on GPU = faster, but more VRAM
    Higher --n-cpu-moe = more experts on CPU = slower, but less VRAM

THE MEASUREMENT (llama-bench, clean machine, gpt-oss-20b-F16, f16 KV, -t 6):

    n_cpu_moe |  prefill pp2048  |  generation tg64
    ----------+------------------+------------------
        24    |  74.75 +/- 0.34  |  6.29 +/- 0.33     <-- USE THIS
        22    |  69.92 +/- 10.00 |  4.48 +/- 0.05

On a 4 GB card the theory does not pay off: there is no headroom to move any
experts onto the GPU. 24 (all experts on CPU) wins on BOTH prefill and
generation. Anything lower is slower AND less stable -- note the +/- 10.00
variance at 22 versus +/- 0.34 at 24. That variance is the tell.

WARNING - the mistake that cost us an hour:
Do NOT run a sweep while llama-server is also running, and do not run two
sweeps at once. The model is 12.83 GiB; two copies do not fit in 31.8 GB RAM.
The result is not an error -- it is silently wrong numbers (we measured the
SAME config at 3.48 and at 75.10 tok/s). tune-moe.ps1 now refuses to start if
llama-server is up, but nothing can protect you from launching it twice.

--------------------------------------------------------------------------------
SCRIPT: D:\ai\bin\tune-moe.ps1   (rev2 - uses llama-bench, not llama-cli)
--------------------------------------------------------------------------------
The original version parsed llama-cli stdout with a regex. That was fragile and
printed "could not parse speed" for every value, hiding the real cause. Use
llama-bench instead: it is built for exactly this and has -ncmoe natively.

    powershell -ExecutionPolicy Bypass -File D:\ai\bin\tune-moe.ps1

Only re-run it if you change MODEL. For Qwen3-Coder-30B (48 layers) pass:
    -Values "48,44,40,36,32"


PRODUCTION CONTEXT - MEASURED, FITS
-----------------------------------
    --n-cpu-moe 24  -c 65536  --cache-type-k q8_0 --cache-type-v q8_0

    VRAM: 3489 / 4096 MiB      (~600 MiB headroom)

Compare: -c 32768 with f16 KV used 3419 MiB. So 64k context with q8_0 KV costs
only 70 MiB MORE than 32k with f16 -- because double the tokens at half the
per-token cost is the same KV cache. There is no reason to run 32k. q8_0 KV is
now ON by default in start-server.ps1; -NoQuantKV turns it off.

Verified working at this config:
  - chat completion            OK
  - tool calling (--jinja)     OK, emits proper tool_calls with escaped JSON


REAL THROUGHPUT - PLAN ON THESE NUMBERS
---------------------------------------
    prefill (prompt processing)      ~75 tok/s
    generation, sustained 600 tok    ~8.3 tok/s     <-- plan on this
    generation, short burst ~100 tok  ~12.5 tok/s

Short replies look about 50% faster than long ones. Do not size the night loop
on a burst number. At ~75 tok/s prefill, a 20k-token prompt costs ~4.5 minutes
BEFORE the first token appears -- so prompt size, not generation speed, is what
governs how many tasks finish overnight. Keep each task's context small.

If you ever see generation around 0.5-1 tok/s, that is not "slow", that is the
CUDA sysmem fallback in section 3 spilling VRAM into system RAM. Go fix it.

--------------------------------------------------------------------------------
THE OPENROUTER BLOCK - optional, and read the limits before you rely on it
--------------------------------------------------------------------------------

The model IDs above are examples. Free model IDs change; check the current
list at https://openrouter.ai/models?q=free and put the exact IDs in the
config. Any ID ending in :free draws on the free quota.

Set the key as a PERMANENT user variable so an overnight run in a fresh shell
can see it:

    [Environment]::SetEnvironmentVariable("OPENROUTER_API_KEY", "sk-or-...", "User")

THE LIMITS THAT ACTUALLY DECIDE WHETHER THIS WORKS OVERNIGHT
    50 requests/day       if you have never bought credit
    1000 requests/day     once you have bought $10 of credit, ever - the
                          threshold is LIFETIME purchases, not your balance,
                          so a single $10 top-up keeps the higher bracket
                          even after you spend it
    20 requests/minute    on :free models, and buying credit does NOT raise it

A task costs roughly 4-6 model calls. So:
    50 req/day    ->  about 10 tasks. Dies in the first hour.
    1000 req/day  ->  about 200 tasks. Covers a whole night with room to spare.

That $10 is the difference between "free tier" being a toy and being a real
overnight executor. Below it, do not plan a night around OpenRouter.

WHY NOT GROQ: the free tier looks generous at 14,400 requests/day, but it caps
at 6,000 tokens per MINUTE. One agent call carrying AGENTS.md plus a couple of
source files is 10-20k tokens, so a single request exceeds the whole minute's
budget. Request count is not the binding limit for coding agents; tokens are.

PRIVACY - the one that matters for client work: OpenRouter gates :free models
behind a prompt-logging/training setting on your account. Check
https://openrouter.ai/settings/privacy before you send a customer's codebase
through it. If the project is under any confidentiality expectation, use the
local model or your Claude subscription instead. Slow and private beats fast
and leaked.

IMPORTANT: the key under "models" must exactly match the --alias you passed to
llama-server.exe. If you switch to Model B, change BOTH the --alias and this
key to the same new string, or OpenCode will send a model name the server
does not recognize.

Smoke test - with the server running, from any project folder:

    opencode run "List the files in this directory and tell me what kind of project this is."

If it reads files and answers, the whole chain works.

13. WHAT COMES NEXT
================================================================================

All three pieces now exist. The workflow guide is the thing to read next:

    D:\ai\workflow\README.txt           how to run a night, start to finish
    D:\ai\workflow\templates\AGENTS.md  the rules file, per project
    D:\ai\workflow\templates\TASKS.md   the queue, per project
    D:\ai\bin\night-run.ps1             the loop itself

Read workflow\README.txt section 0 before anything else: it explains why the
loop exists at all, and section 4 explains how to size a task, which is the
part that decides whether a night works.

Do NOT point the loop at a real project before running it once on a throwaway
repo. A loop running against an untuned server or a vague queue just produces
8 hours of garbage commits very slowly.
