THE GUI
-------

    start-gui.bat          (or: python gui\app.py)

    Browse to a project  ->  Settings: Set up this project
                         ->  Settings: Apply stack
                         ->  Run: Dry run
                         ->  Run: with CLAUDE / with GEMINI / AUTO

    Every run opens in its OWN titled terminal window, so a Claude run and a
    Gemini run are two separate things you can watch and kill independently.

    The Tasks tab lists what the runner will actually pick up - it uses the
    same comment-aware scan, so what you see is what will run.

The GUI is only a front end. Everything below is the same thing by hand.


THE FOUR COMMANDS
-----------------

    # ONCE per project - safe on a project you already have,
    # it never overwrites a file that exists
    .\bin\new-project.ps1 -Root "D:\work\acme-site"

    # EVERY time, before you trust it - no model calls, no writes
    .\bin\night-run.ps1 -Root "D:\work\acme-site" -DryRun

    # the run  (-Executor opencode = free Gemini, claude = subscription,
    #           auto = claude then Gemini)
    .\bin\night-run.ps1 -Root "D:\work\acme-site" -Executor opencode

    # the morning after
    cd D:\work\acme-site
    git log --oneline
    Select-String TASKS.md -Pattern '\[!\]'

That is it. Everything below is detail on the one step that actually decides
whether the night works.


--------------------------------------------------------------------------------
STEP 0 - THE PART THAT DECIDES EVERYTHING: WRITING TASKS.md
--------------------------------------------------------------------------------

The runner is plumbing. The queue is the work. A well-written queue with a
weak model beats a vague queue with a strong one, every time.

You do not have to write it by hand, and you should not have to remember what
to type either. In the GUI:

    Tasks tab -> "Write tasks with Claude..."
        pick what Claude should read, choose how many tasks,
        then "Copy and open Claude here" and paste with Ctrl+V

    Tasks tab -> "Fix blocked tasks..."
        the same thing for the morning review of [!] tasks

The prompts live in workflow\prompts\ as plain markdown - write-tasks.md and
unblock.md. Edit them once and every project gets the improvement. They carry
the task-sizing rules, the append-never-overwrite rule, and the
test/implementation split, which is why they are worth more than a sentence
typed from memory.

Writing the queue is the highest-value thing to use Claude for here. Keep that
job; hand the mechanical typing to the free model.

A task is the right size when it is:
    * ONE file, or one file plus its test
    * about 30 lines of code or fewer
    * verifiable by the test suite alone, with no judgement call
    * stated with EXACT names - path, class, method, column, route

    TOO BIG - the model wanders, tests fail, you get [!]:
        - [ ] Build the products module
        - [ ] Add authentication

    RIGHT SIZE:
        - [ ] Create migration create_products_table with columns: id,
              name string(255), price decimal(10,2), stock int default 0
        - [ ] Create model app/Models/Product.php with fillable name, price, stock

ORDER MATTERS. The runner commits after each task, so later tasks build on
earlier ones. Migrations -> models -> requests -> controllers -> routes.

NEVER PUT A TEST AND ITS IMPLEMENTATION IN THE SAME TASK. A task that can edit
both can always make them agree. Write the tests yourself (or have Claude write
them); the runner rejects any untagged task that modifies a test file.


--------------------------------------------------------------------------------
AGENTS.md AND STACK PRESETS
--------------------------------------------------------------------------------

AGENTS.md is the rules file, re-sent on EVERY model call. Keep it under ~150
lines and write it for a model that does not infer:

  IGNORED - abstract, nothing to pattern-match on:
      "Write clean, maintainable code."   "Follow SOLID principles."

  OBEYED - short, imperative, with a right/wrong pair:
      "Never query inside a loop."
          WRONG:  foreach ($orders as $o) { Customer::find($o->customer_id); }
          RIGHT:  Order::with('customer')->get();

Presets live in workflow\templates\stacks\ - Laravel + React,
Node + Prisma + React, Flutter, Generic. Apply one from the GUI's Settings tab,
or copy the file to AGENTS.md by hand.

AFTER APPLYING ONE, OPEN IT. Replace the example versions and commands with
this project's real ones. The model has no other source for them, and a wrong
command in AGENTS.md is worse than none.


--------------------------------------------------------------------------------
WHO WRITES THE CODE
--------------------------------------------------------------------------------

    -Executor auto       DEFAULT. claude -> opencode. Claude until its usage
                         window closes, then free Gemini finishes the queue.
    -Executor claude     subscription only. Strongest.
    -Executor opencode   free only. google/gemini-3.5-flash-lite,
                         1000 requests/day, about 200 tasks. Costs nothing.

Useful flags:
    -DryRun              list the queue and exit
    -TaskTimeoutMin 25   per-task hard timeout (default 20)
    -MaxRetries 0        no retry (default 1)
    -ClaudeModel opus    for a queue of harder tasks
    -TestCmd "php artisan test"      override the auto-detected test command

Test command is auto-detected:
    artisan -> php artisan test      pubspec.yaml -> flutter test
    package.json + test -> npm test  pyproject.toml -> pytest -q


--------------------------------------------------------------------------------
READING THE MORNING
--------------------------------------------------------------------------------

    [x]  done, committed. The queue mark and the code are in the SAME commit.
    [!]  blocked and rolled back. Nothing of it survives in the tree.

A [!] is usually NOT the model being stupid. In order of likelihood:
    1. the task was too big or ambiguous       -> split it, re-queue as [ ]
    2. the test was wrong                      -> this happens; check it first
    3. a rule AGENTS.md never actually stated  -> add the rule
    4. the model genuinely failed              -> least common

    Full transcript:   .agent\task-<stamp>-NNN.log
    Test output:       the matching .tests file

Re-queue a fixed task by changing [!] back to [ ].


--------------------------------------------------------------------------------
THINGS THAT WILL BITE YOU
--------------------------------------------------------------------------------

DIRTY TREE
    Preflight refuses to start. That is deliberate: a rollback would destroy
    your own uncommitted work. Commit or stash first.

THE TEST COMMAND MUST ALREADY PASS
    Preflight runs it once on a clean tree and refuses to start if it is red.
    Every task is graded by that command, so a broken environment marks the
    WHOLE queue [!] for a reason that has nothing to do with the model.
    Before your first run on a project:
        Laravel   composer install, and uncomment the sqlite lines in
                  phpunit.xml so tests get a database:
                      <env name="DB_CONNECTION" value="sqlite"/>
                      <env name="DB_DATABASE" value=":memory:"/>
        Node      npm install, and make sure `npm test` EXITS - bare `vitest`
                  watches forever; use `vitest run`.
    -SkipBaseline starts anyway, if you know why you want that.

STALE LOCK after a hard kill
    Handled for you: the lock records its owning process id, so a lock left by
    a killed run is reclaimed automatically on the next start. Only a lock
    whose process is genuinely alive blocks a run. The GUI has a Clear stale
    lock button for the rare leftover from an older version.

A GREEN SUITE IS NOT A GOOD-LOOKING SITE
    The test gate grades what a test can see. For a company website the things
    that matter most - layout, copy, responsiveness, whether it looks
    professional - are exactly what the suite does not check. Queue the backend
    overnight; do the visual layer interactively, where you can look at it.

THE QUEUE, NOT THE MODEL, IS YOUR CEILING
    A task takes 30-60 seconds now. An 8-hour night would need ~500 tasks and
    nobody writes 500 good ones. So this is no longer really an overnight tool:
    write a queue, run it, review it, fix the queue, run again - several times
    a day. That loop teaches you more than any night ever did.

LAPTOP ASLEEP for a genuinely long run
    powercfg /change standby-timeout-ac 0
    powercfg /change hibernate-timeout-ac 0


--------------------------------------------------------------------------------
IF SOMETHING IS NOT WORKING
--------------------------------------------------------------------------------

Run the demo. It is four pre-written tasks with a pre-written test gate, and it
is known to pass 4/4 on the free tier:

    .\bin\new-project.ps1 -Root "D:\work\starter-demo" -Starter
    .\bin\night-run.ps1  -Root "D:\work\starter-demo" -Executor opencode

If the demo passes, the setup is fine and the problem is in your queue.
If the demo fails, the preflight line in the output names what is missing.
